# 待办：前端测试体系

创建：2026-10-16 · 状态：待办 · 优先级：中

## 背景

前端目前**零测试框架**——`frontend/package.json` 里没有 `test` 脚本，也没有 vitest／jest 依赖；CI 的 frontend
job 只做类型检查与构建（`.github/workflows/ci.yml`），所有前端逻辑都靠人肉验证。

本次「组次用时恒为 `00:00`」正是这类漏洞的样本：出错的 `src/utils/session.ts` 里 `setDurationSec` /
`lastDoneAt` / `pausedMsBetween` 是一段**纯口径计算**，不碰 UI、不碰网络，本该被单测一眼抓住，结果一路带出
线上，v0.8.0～v0.8.2 三个版本提交的训练记录全是脏数据（勘误见 CHANGELOG 的 `[Unreleased]` 段）。

同类纯函数还有一批：`utils/session.ts`（净时长、暂停区间、组次用时）、`utils/format.ts`（`formatClock`、
`formatDuration`）、`utils/diet.ts`、`utils/weight.ts`（斤／千克换算与精度）。

## 可选方案

- **方案甲：引入 vitest，只覆盖 `src/utils/` 的纯函数**——加 devDependency ＋ `test` 脚本 ＋ CI 步骤，先补
  `session.ts` 的口径用例（先算后写、跨动作取上一组、暂停段剔除、撤回后回退）。代价：新增依赖与一条流水，
  本轮交付会变重，所以本次没做。
- **方案乙：把这些口径挪到后端算**——前端只上报时间戳。代价：会话数据按
  [ADR 0020](../adr/0020-session-local-persistence-and-wall-clock-timer.md) 存在本机、离线也在计时，
  后端根本没有那段数据；此路不通。
- **方案丙：维持现状**——靠 `docs/design/前端.md` 里的 ⚠️ 条目与 review 兜底。代价：纯计算类的错误照样能
  悄悄发版，本次已经演示过一遍。

➡️ 倾向：**方案甲**，但**不在本轮做**——等第二处同类口径逻辑出现时一并引入，避免为单点落地一整套流水。
方案乙不可行；方案丙兜不住这类错误。

## 待确认

引入时机由主人定。真要落地时还需决定测试在 CI 里跑还是只在本地跑。
