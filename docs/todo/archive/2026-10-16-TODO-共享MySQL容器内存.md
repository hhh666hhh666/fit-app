# 待办：共享 MySQL 容器内存

创建：2026-10-16 · 状态：已解决 · 优先级：高

## 背景

`quizzy-mysql` 容器（内存上限 **384MB**，定义在 quizzy 仓库的 `compose/docker-compose.prod.yml`）被内核
OOM-killer 杀掉了**三次**：2026-10-14 14:59、2026-10-16 09:37、2026-10-16 13:07（`dmesg` 里的 `oom_memcg`
指向该容器的 cgroup）。每次重启之间有约十秒，这段时间里 fit-app 与 quizzy 的连接池整体失效，写请求必失败——
fit-app 侧表现为**上传餐照**偶发「系统繁忙，请稍后再试」（见 [ADR 0005](../../adr/0005-deploy-with-quizzy-infra.md) 的共享实例口径）。

直接的推力是餐照：它是本项目**唯一**向数据库写数 MB 大字段的接口（`meal_photo.image` 为 `MEDIUMBLOB`），
插入时 InnoDB 要在缓冲池之外额外分配行缓冲，正好压在这块 384MB 的天花板上。fit-app 侧已做止血
（写库遇瞬时故障自动重试 ＋ 明确文案），但那只是让用户端不至于看到含糊提示。

## 可选方案

- **方案甲：调小 MySQL 自身的内存项**——`innodb_buffer_pool_size` 128M → 64M（确定性与内存直接相关，省 64MB）；
  可再顺带 `mysqlx=OFF`（关 X Plugin，省十几 MB）与 `innodb_redo_log_capacity` 100M → 48M
  （后者省的是**磁盘**、不省内存，只是让 InnoDB 初始化时少些开销）。代价：缓冲池小一半，冷查询略慢——
  本项目是自用小工具、写入量小且无并发，感知不到。
- **方案乙：抬高容器内存上限**——把 384MB 调到 512MB 或以上。代价：宿主总内存仅 **1870MB**、当时可用只剩
  约 **560MB**，而各容器限额之和（384＋640＋128＋640＋128＝1920MB）本就**已经超卖**。抬 MySQL 等于把压力
  转嫁给整机，很可能从「杀 MySQL」变成「杀别的容器」，是换一种故障而非消除故障。
- **方案丙：餐照不再进数据库**——图片落服务器文件系统，库里只留路径。代价：牵动
  [ADR 0013](../../adr/0013-photo-storage-and-quota.md)、[ADR 0014](../../adr/0014-photo-viewer-and-album.md)、
  存量数据迁移与备份方案，工程量大；但它同时把备份体积（图片主导）一并解决，宜作中期方向。

➡️ 选择：**方案甲**——低风险、直接削弱触顶根因，且不改动机器的内存总量。

## 待确认

（已定）由荧执行，2026-10-16 21:00 落地。改动落在 **quizzy 仓库**的编排文件，参数生效靠重建该容器——
实测中断 **9 秒**（20:56:13 → 20:56:22 healthy），比预估的十秒还短。

⚠️ 两个跨项目的后效应记在这里，免得接手的人以为是自己弄坏的：

- **在线缩小缓冲池这条路是死的**：`SET GLOBAL innodb_buffer_pool_size` 会被 Warning 1210 拒绝
  （缓冲池不能小于一个 chunk）。降 pool 必须在启动参数里**同时**降 `innodb_buffer_pool_chunk_size`
  （默认 128M、且非动态参数），否则 MySQL 启动时会把它向上取整回 128M——改了等于没改。
- 服务器上那份编排是**手动 scp 上去的派生副本**：quizzy 下次发版会被仓库版本整体覆盖。所以真相源的改动
  已一并提交在 quizzy 仓库，不依赖服务器上那一份。
