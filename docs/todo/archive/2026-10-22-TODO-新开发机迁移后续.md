# 待办：新开发机迁移后续

创建：2026-10-22 · 状态：已解决 · 优先级：中

## 结论
2026-10-24 按方案甲做了：`docker-compose.dev.yml` 改用命名卷 `fit-app-mysql-data`，`.env.example` 去掉 `MYSQL_DATA_DIR`。口径（为什么、怎么备份 / 清库、旧机器怎么搬数据）写在 [`docs/operations/configuration.md`](../../operations/configuration.md)「本机数据库数据：命名卷」一节。

## 背景
换开发机时暴露出一个与具体机器无关的问题：在 Windows 上，`docker-compose.dev.yml` 把 MySQL 数据目录绑定挂载到宿主机盘（`MYSQL_DATA_DIR`）。经 WSL 跨文件系统读写很慢，首次初始化可能超过 healthcheck 的等待时长，先被判成 unhealthy；MySQL 还会因为挂载目录不区分大小写，自动设成 `lower_case_table_names=2`，与 Linux 服务器（区分大小写）不一致，表名大小写写错在本机发现不了。

## 可选方案
- **方案甲（采用）**：`docker-compose.dev.yml` 改用命名卷（数据留在 Docker 自己的 Linux 文件系统里）—— 代价：数据不再是仓库旁一个可见目录，备份 / 清库要走 `docker volume`。
- **方案乙**：保持绑定挂载，只在 `docs/operations/configuration.md` 写明 Windows 上首次启动慢与大小写差异 —— 代价：大小写差异仍可能漏到线上。

## 验收
在一台 Windows 开发机上实测：
- 旧容器（绑定挂载）：`@@lower_case_table_names` = 2，问题确实存在。
- 先 `mysqldump` 旧库，再用新 compose 重建容器：命名卷上初始化约 42 秒就 healthy，`@@lower_case_table_names` = 0。
- 导回 dump：20 张表、30 条 Flyway 记录都在，没有大写表名；本机裸跑后端，Flyway 校验 30 条迁移通过、启动正常。
