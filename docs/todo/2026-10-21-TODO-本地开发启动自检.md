# 待办：本地开发启动自检

创建：2026-10-21 · 状态：待办 · 优先级：中

## 背景

2026-10-21 凌晨 `start-dev.ps1` 选 1，前端起来了、后端失败，控制台只有一句「启动失败，详情见 `.workbuddy\backend-run.log`」。打开日志才是三层叠加的故障：

1. **Docker Desktop 没跑** → `fit-app-mysql` 容器不在 → 3307 无人监听 → Flyway `Connection refused`
2. 库通了之后撞上第二层：`target/classes/db/migration/` 里残留着旧编号的 `V25__plan_per_set_targets_and_circuit.sql`（源里已重编为 V26），与 `V25__meal_photo_to_file.sql` 撞版本 → Flyway `Found more than one migration with version 25`。Maven 增量编译只复制、不删除已删源文件的产物，所以只要重新编过号就必然残留
3. `mvn clean` 之后又撞第三层：沙箱注入的 `SERVER__PORT=63444` 被 Spring 的 relaxed binding 当成 `server.port`，报「Port 63444 was already in use」——脚本里其实已有 `Remove-Item Env:\SERVER__PORT`，但那行只管住了脚本自己拉起的进程，经荧手动启动时没被覆盖

前两层排查顺序完全依赖人工读日志，且第 2 层的报错文案（「more than one migration」）不会提示「该 clean」。

## 可选方案

- **方案甲**：`start-dev.ps1` 启动后端前做三项自检——`docker info` 能否连通、3307 能否连、`target/classes/db/migration` 里版本号是否重复；任一不过就直接打印可读原因（「Docker 没启动，先开 Docker Desktop」「迁移脚本版本号重复，需要 mvn clean」）并跳过后端启动 —— 代价：脚本多几十行，且自检逻辑本身要跟目录约定同步维护
- **方案乙**：每次拉起后端前无条件 `mvn clean` —— 代价：每轮开发多 20~30 秒，绝大多数时候并不需要，属于用时间换确定性
- **方案丙**：不动脚本，把这三层故障写进 `docs/operations/` 的排障条目 —— 代价：下次仍要靠人先想到去翻文档

➡️ 倾向：**方案甲**。第 1、3 项自检几乎零成本（Docker 与端口都是现成命令），第 2 项只需读目录里的文件名前缀，比每次 clean 划算得多；而且它把「控制台只报一句失败」这个真实痛点直接补上。
