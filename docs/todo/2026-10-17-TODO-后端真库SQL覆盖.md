# 待办：后端真库 SQL 覆盖

创建：2026-10-17 · 状态：待办 · 优先级：中

## 背景

后端目前**一个 `*IT` 都没有**：`mvn test` 全绿只证明 service 逻辑对，注解里的 SQL 文本**一次都没被 MySQL 执行过**。2026-10-17 计划列表与统计接口 500（「系统繁忙」）正是这么上的线——`@Select` 里写了 `&lt;&gt;` 而语句没有 `<script>` 包裹，编译与 mock 单测都发现不了。

`scripts/check-mapper-sql.sh` 只机械兜住「无 `<script>` 却含 HTML 实体」这一种形态，列名拼错、语法关键字错、迁移与实体不一致仍然只能靠真库或线上日志。`release.yml` 里已有一个「在一次性 mysql:8 上跑完整迁移」的 job——起库的成本其实已经被付过一次了。

## 可选方案

- **方案甲**：在 `release.yml` 那个迁移 job 后面加一步「mapper 冒烟」：迁移跑完后，把注解 SQL 里的 `#{...}` 换成常量、逐条 `PREPARE`/`EXPLAIN`，语法不通即失败 —— 代价：要维护一个「从 Java 里抽 SQL」的小脚本（与 `check-mapper-sql.sh` 共用解析），`<script>`/`<foreach>` 这类动态 SQL 抽不干净，得白名单跳过。
- **方案乙**：补少量 `*IT`（Testcontainers 起 MySQL + 跑迁移），只覆盖高频读接口的 mapper —— 代价：本机跑 `mvn verify` 要 Docker；CI 多一个 job 与几分钟；`IT` 会随功能增长要求同步维护。
- **方案丙**：不补，维持「守卫脚本兜一类 + 上线看日志」 —— 代价：同类事故下次仍然要等用户先撞上。

➡️ 倾向：**方案乙**。理由是它同时回答了另一件现在没人回答的问题——「迁移脚本与实体字段到底对不对得上」（本次事故的邻居风险）；而方案甲的 SQL 抽取在动态 SQL 上永远抽不干净，投入产出比更低。范围收在 3～4 个高频读接口即可，不求全覆盖。

## 待确认

- 是否接受 `mvn verify` 从此需要 Docker（本机与 CI 都是）。
- 优先级与时机：等功能开发告一段落再补，还是下次动 mapper 时顺手补。
