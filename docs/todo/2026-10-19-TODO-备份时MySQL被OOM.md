# 待办：共用 MySQL 在备份时被 OOM

创建：2026-10-19 · 状态：待办 · 优先级：高

## 背景

2026-10-19 18:28 发 v0.12.0 时，部署前的强制备份（`scripts/backup-mysql.sh`，走 `docker exec … mysqldump`）
把 `quizzy-mysql` 顶到 384MB 上限，内核在 18:31:11 直接 OOM-kill 掉 `mysqld`（`dmesg` 的 `oom_memcg`
指向该容器，容器随后就地重启）。备份因此产出 2.8K 的半截文件、脚本非零退出，`server-deploy.sh`
按 [ADR 0026](../adr/0026-photo-storage-and-backup.md) 中止部署——**服务没被换掉，但发版失败**；
同一条流水线重跑一次（MySQL 刚重启、占用回到 208MB）就成功了。

历史上同名问题在 [2026-10-16 已结案](./archive/2026-10-16-TODO-共享MySQL容器内存.md)：当时把
`innodb_buffer_pool_size` 压到 64M、关掉 X Plugin，占用从 315MB 降到 146MB。三天后今天是
**208MB / 384MB**（余量约 176MB），一次 dump 的内存尖峰就够把它推过线。也就是说旧方案把「写大字段
顶爆」换成了「备份顶爆」，天花板本身没动。

⚠️ **2026-10-19 20:05 实测修正**：dump 本身只值 **6–7MB**——容器内跑一次全量 dump，cgroup 峰值
255.1 → 261.2 MiB（+6.2MiB，mysqld HWM +5.6MiB），耗时 **0.086 秒**；宿主直连 dump 的峰值 RSS
**8.4MB**、0.10 秒。所以「dump 的尖峰吃掉 150MB」不成立，18:31 那次 OOM 的推力在别处：
重启后容器 usage 已 259MB，其中 **rss 219.7MB（`rss_huge` 190MB，透明大页）＋ 页缓存 39.6MB**，
mysqld 常驻本身就 230MB，余量只剩约 125MB。昨晚那 156 秒也不是 dump 慢，是 MySQL 早就在顶着上限换页。

## 可选方案

- **方案甲：备份改从宿主直连 dump**（`mysqldump -h127.0.0.1 -P3306 -uroot`，口令仍从 `/srv/fit-app/.env` 读）——
  代价：`mysqldump` 进程不再计入容器 cgroup，但要接受「备份依赖宿主客户端与 root 账号」；
  宿主已有 `/usr/bin/mysqldump`、3306 只绑 `127.0.0.1`，2026-10-19 实测可通（含全量 dump）。
- **方案乙：抬高 `quizzy-mysql` 的 `mem_limit`**——代价：跨项目改 quizzy 编排，且整机本来就超卖
  （见 [内存策略](../operations/内存策略.md) §二）；旧结论是把「杀 MySQL」变成「杀别的容器」。
  ⚠️ 本机**没有 quizzy 仓库**，只能改服务器上的派生副本，会被 quizzy 下次发版覆盖——真要改必须先拿到它的仓库。
- **方案丙：备份前加内存闸 ＋ 原子落盘**——余量低于阈值就明确失败；先写 `.part`、`gzip -t` 与非空校验
  通过才改名，失败用 `trap` 清掉临时文件——代价：治标；部署在余量不足时会被挡住（挡住总比带病迁移好）。
- **方案丁：查透明大页与 mysqld 常驻**——取证已完成（2026-10-19 20:20，`/proc/<pid>/smaps`）：
  - 555 个映射、RSS 249MB，其中大页 **198MB**；大页集中在 **12 个匿名 `rw-p` 映射**里
    （92.8 / 38.6 / 32 / 16 / 11.5 / 11.3 / 8.6 / 6.9 / 6.4 / 5.5 / 5.3 / 3.4 MB），
    这 12 个映射的 RSS 合计 208MB，**大页占其 RSS 的 95%**。
  - 也就是：**大页不是「虚胖」**——映射被真实写满了，THP 的取整浪费只有个位数 MB。改 THP 省不出几十 MB，
    最多省「映射尾部没被写满」的那点（区域合计 238MB、RSS 208MB）。
  - 常驻的真实构成：缓冲池 64MB ＋ 剩下约 144MB 的分配器／线程／表缓存（`performance_schema` 已关，
    没有现成的内存仪表可再细分）。宿主 THP = `always`（`tuned` 配置档 `ecs-performance`）。
  - 结论：**THP 不是主因，抬 `mem_limit` 才是对症的那一半**；要看清 144MB 得临时开 `performance_schema`
    （它自己也要吃内存），代价与收益不成比例，暂不做。
  - 另：20:20 采样 90 秒里 usage 从 263 → 265MB 缓慢上涨、连接数稳定在 11、大页恒为 198MB——
    趋势还需更长观察，不能据此下「泄漏」的结论。

➡️ 倾向：**备份脚本暂不改**——甲 ＋ 丙 曾于 20:13 落地，20:27 按主人要求整体回滚，
线上与仓库都回到「容器内 dump」的旧脚本。按丁的取证，THP 不是主因，抬 `mem_limit` 才是对症的那一半；
但它要动 quizzy 仓库并伴随一次 1–9 秒重启，等主人拍板。拍板前维持现状；旧脚本「失败会留半截文件」的风险仍在背景里。

## 待确认

- 备份是否改用独立的只读账号（现在与 `docker exec` 路径一样直接用 root）——不建也能跑，属安全加固。
- 18:28 那次留下的 `fit_app-20261019-182835.sql.gz.partial` 已改名隔离，是否保留待查后删除。
- **要不要动内存参数**（`mem_limit` 384 → 512）：需要一次 1–9 秒的 MySQL 重建，且真相源在 quizzy 仓库。
