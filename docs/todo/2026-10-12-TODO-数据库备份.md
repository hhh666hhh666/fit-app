# 待办：数据库备份（fit_app 库）

创建：2026-10-12 · 状态：待办 · 优先级：高

## 背景

fit-app 已于 2026-10-12 上线（v0.1.1，`fit.11-2.cn`）。数据放在 **quizzy 的 MySQL 容器**里
（`quizzy-mysql`，[ADR 0005](../adr/0005-deploy-with-quizzy-infra.md) 方案 A），两边目前**都没有任何自动备份**：`server-deploy.sh`
每次部署都会打印「⚠️ 没有 backup-mysql.sh，跳过部署前备份」，而线上也没有定时快照。

一旦发生误操作（误删记录）、容器重建或磁盘故障，**训练数据全部归零且不可恢复**——
这是当前唯一「出事会真的疼」的项。主人 2026-10-12 明确「先立待办，暂不实现」。

## 可选方案

- **方案甲：独立 dump 脚本 + crontab**——`docker exec quizzy-mysql mysqldump fit_app` 打成带日期的 `.sql.gz`，
  放服务器本地目录，crontab 每天跑，本地留 N 天。代价：只覆盖 fit_app，不覆盖 quizzy 的库（那仍是 quizzy 的待办）。
- **方案乙：让 quizzy 的备份套路带上 fit_app**——如果 quizzy 已有/将来有备份脚本，把 `fit_app` 加进它的库清单。
  代价：两个项目的备份策略耦合，改 quizzy 的脚本会连带影响本项目。
- **方案丙：整库备份**（`mysqldump --all-databases`）。代价：每次都含 quizzy 的数据，体积与时间翻倍，且与 quizzy 的备份策略重叠。

➡️ 倾向：**方案甲**（独立、互不影响、最快落地）；若 quizzy 那边后补了备份，再按方案乙合并，减少一份重复的 crontab。

## 待确认

- 保留几份、多久一轮（倾向：每日一份、留 7 天；可配）。
- 备份放服务器的哪个目录（倾向 `/srv/fit-app/backups/`，与 compose 数据目录分开，避免容器重建时一起没）。
- 要不要顺手把备份**拉到本机**（rsync/ scp）——服务器单机备份不防「整机挂掉」，但 N=1 自用可接受。

## 更新记录

- 2026-10-12：创建（上线后第一件被明确排期的收尾项）。
- 2026-10-12：饮食记录落地（v0.3.0）——餐照**以 MEDIUMBLOB 直存 MySQL**，备份从此还要覆盖图片：`mysqldump` 的体积/耗时将随照片增长，每日 dump 前先估容量；本条优先级维持「高」。
- 2026-10-13：需求打磨中为图片定了 **20 GB 容量上限**（暂时只算图片）。这条上限把本待办的形态逼了出来：图片留在库里，`mysqldump` 导出的体积会被图片主导——按默认压缩档估算约 45 年才触顶，但若长期用「无损」档约三年半即到上限。落地备份方案时必须同时决定**图片是否仍留在每日 dump 里**（例如结构化数据每日 dump、图片另行增量同步到对象存储），否则「每日全量」这条路线在最坏情况下会变得不可执行。
- 2026-10-16：v0.8.3 发版前手工做了一次性 dump（迁移 V22 要改数据，而 `deploy/README.md` 要求部署前必须先备份）——落在服务器 `/srv/fit-app/backups/fit_app-20261016-200439.sql.gz`。**这是一次性应急备份，不是本待办的落地**：仍然没有脚本、没有 crontab、没有保留策略，下次部署照样打印「跳过部署前备份」。顺带一条实测：库内 `data_length + index_length` 只有 **1.4 MB**，dump 出来却是 **15 MB** —— 差距来自两张餐照（`MEDIUMBLOB` 转十六进制文本的膨胀）与扩展插入，正好印证上面那条「体积会被图片主导」的判断。
