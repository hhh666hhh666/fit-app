# 待办：移动端流畅度优化

创建：2026-10-20 · 状态：待办 · 优先级：中

## 背景

主人反馈 App「点图标后白屏几秒」「切页、点按钮要等一下」，怀疑必须打包成原生才能解决。2026-10-20 做了一轮实测诊断，结论是**「打包成原生」不对症**——形态上已经是 apk（`android-shell/` 的 WebView 壳，[ADR 0002](../adr/0002-android-app-uni-app-shell.md)），缺的不是「打包」而是「原生渲染」，而那是拿全部页面重写换来的，对自用工具不划算。

**已排除的嫌疑（都有实测）**：

| 嫌疑 | 实测 | 判定 |
|---|---|---|
| 后端慢 | `/api/exercises` TTFB 67~96 ms（连测三次） | 排除 |
| 没压缩／带宽 | 主 JS 原始 280 KB → gzip **98 KB**，0.11 s；`Content-Encoding: gzip` 生效 | 排除 |
| 静态资源重复下载 | `/assets/` 带 hash 且 `immutable, max-age=31536000` | 排除 |
| CSS 重特效 | `backdrop-filter` 0 处、`transition: all` 0 处、`box-shadow` 5 处 | 排除 |

**锁定的四个真凶**：

1. **HTML 的 `no-store` 把 ETag 废掉了**：线上 `/` 响应**同时带两个 `Cache-Control`**——宿主 nginx 的 `no-cache` 与 `frontend/nginx.conf` 里 `add_header ... always` 的 `no-cache, no-store, must-revalidate` 叠加。`no-store` 优先级更高，浏览器连 ETag 都不存，于是每次冷启动都全量重拉 HTML（374 ms 量级）＋ 重做 TLS，`Last-Modified`/`ETag` 形同虚设。
2. **`<div id="app">` 是空的**：线上 HTML 为 `<div id="app"><!--app-html--></div>`，纯客户端渲染、无内联骨架、无背景色——JS 解析执行完之前屏幕**纯白**，没有任何反馈。这是「白屏」的直接观感来源。
3. **主包解析执行是固定成本**：98 KB gzip 之后仍要解析执行 Vue 3 ＋ uni-app 运行时后才渲染首帧，中低端机型上这段是白屏的大头，且无法靠网络优化掉。
4. **切页 chunk 懒加载且无加载态**：各页产物是独立 chunk（`pages-*-index.js`，10~26 KB），首次进某页才 `import()`，要等一个 RTT；而页面切换期间没有任何骨架或转场，等待被直接感知为「卡了一下」。

另有一处**独立隐患**（当前症状不指向它，但仍应记着）：`pages/session/index.vue` 的 `deep: true` watcher 是全仓唯一一处深监听，命中即调 `saveSession()`，而 `utils/session.ts` 的落盘是 `uni.setStorageSync`（H5 下＝`localStorage.setItem`，**同步阻塞主线程**）＋ 整份 `JSON.stringify`。训练录入时每敲一个数字就全量序列化写盘一次。若将来出现「录组次打字延迟」，就是它。

## 可选方案

**低成本组（前端口径 ＋ 壳小改，不动架构、不违背 ADR 0002）**

- **改 HTML 缓存头**：`frontend/nginx.conf` 的 `index.html` 段去掉 `no-store`，只留 `no-cache`——仍然每次向服务器确认，但走 304、无 body，几百字节；同时让 ETag 真正生效。顺带查清宿主层那个重复的 `no-cache` 从哪来的（宝塔模板），必要时在宿主侧统一。代价：一行配置，需实测确认 304 生效且「新版仍即时上线」。
- **H5 启动骨架**：在 `index.html` 的 `<div id="app">` 内放内联骨架（背景色 ＋ 居中 logo／占位块），Vue 挂载后自然覆盖。零额外请求、零依赖。代价：骨架要跟首屏结构大致对齐，否则会有一次轻微跳动。
- **壳侧启动占位**：`MainActivity` 给 WebView／根布局设背景色与居中标识，`onPageFinished` 后淡出——把「连 HTML 都还没到」的那几百毫秒也遮住。代价：动壳要重打 apk 才生效（一次即可）。
- **切页反馈**：页面切换期间加骨架或轻转场，让「等一下」变成「有反馈」。

**重量级**

- **H5 产物嵌进 apk**（`file:///android_asset/`）：白屏与切页的网络等待**彻底消失**，chunk 也全在本地。代价：每次前端更新都要重打并重装 apk，正面放弃 [ADR 0002](../adr/0002-android-app-uni-app-shell.md)「网站更新手机端即时生效」这条核心取舍；若要保留即时更新，得再做「内嵌兜底 ＋ 后台拉新版离线包」的双轨，工程量数倍。
- **换原生渲染**（nvue／app-plus 或 Kotlin 重写全部页面）：代价是整个前端重做，不推荐。

➡️ 倾向：**先做低成本组，按「改缓存头 → H5 启动骨架 → 壳侧占位 → 切页反馈」的顺序，每步单独验证再进下一步**。理由是这四项加起来能把「白屏」与「切页等待」的**感知**压掉大半，而风险面只涉及一个 nginx 配置段、一段内联 HTML 和壳的 20 行代码；内嵌 apk 留作最后手段——只有当前四项做完仍不满意时才值得付那个代价。

## 待确认

- **部署与真机验证**：`scripts/build-apk-web.sh` 的产出（`dist/build/h5/web/`）要随站点一起上线，服务器 `.env` 要加 `FITAPP_CORS_ALLOWED_ORIGINS=https://appassets.androidplatform.net`；漏配的症状是「App 里页面能开、数据全是网络异常」。
- 真机上白屏还剩多少（本地加载后仍要解析执行主包，这一段需要实测才有数）。
- 启动骨架与切页反馈是否还值得做：双轨落地后白屏窗口已大幅收窄，若实测仍嫌长得补 H5 侧内联骨架。
