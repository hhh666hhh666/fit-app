# 食物图片：每条食物一张方形封面，只存截好的方图和缩略图

Status: accepted · 2026-11-15

主人想给食物库里的食物设一张图片，在列表里一眼认出它。这张图是食物的**封面**，不是照片存档：每条食物最多一张，不进相册，饮食记录里也不显示。

## 决策

1. **谁能设**：和别名一样，谁能改这条食物的名字，谁就能设它的图片。自建食物由用户自己设；预置食物由管理员在管理端设，所有人都看得到。普通用户不能给预置食物设只有自己看得到的图。
2. **来源与存储**：在 App 里拍照或从相册选图，再用头像那个方形裁剪框（`AvatarCropper`，预览改成圆角方形）取景。服务端按裁剪框截图，**只存边长不超过 800 的方图和一张 240 的缩略图，不留原图**；原图比这更小时按原尺寸存，不放大。管理端没有裁剪框，上传后居中截取短边。
3. **文件位置**：自建食物在 `{photo-dir}/{userId}/food/{imageKey}`，注销账号时随用户目录一起删除；预置食物在 `{photo-dir}/preset/food/{imageKey}`。`imageKey` 是随机串，换图就换新的，前端把它当作缓存版本号，所以不用手动作废缓存。
4. **空间**：自建食物的图片算进这个用户 20GB 的照片空间，但不进相册，也不计入张数（做法同头像）。预置食物的图片是系统数据，不算进任何人的空间。
5. **换图、去掉图、删除食物**：换图或去掉图时，旧文件直接删除，不进回收站。删除整条自建食物时，图片跟着食物进回收站（文件留在原处，期间照样占空间），恢复时一起回来，彻底删除时才删文件。
6. **跟着走的流程**：「复制为自定义」会把图片文件复制一份，两边各自独立，新的那份算进用户的空间。JSON 导入导出（个人和管理端都算）不带图片。不给预置食物成批配图：一来没有现成的图源，二来网上的图有版权问题。
7. **显示**：详情页顶部一张方形大图。食物库列表、记一餐的选食物弹层、组合编辑里，有图的行左边显示一张小缩略图；没图的行保持原样，不留空占位，因为 1800 多条预置食物大多不会有图。

## Considered Options

- **像头像那样保留原图、以后可以重新取景**：否。食物图只是用来辨认的封面，没必要多占一份原图的空间。
- **一条食物可以有多张图**：否。封面一张就够；要存档照片有「拍照记录」。
- **列表里没图的行也留一个占位格**：否。绝大多数行都会是空格子，平白占掉一列。
- **饮食记录里也显示食物图片**：否。记录存的是当时的快照，食物后来换了图，不该影响历史。

## Consequences

- 接口：`POST /api/foods/{id}/image`（multipart：`file` ＋ 可选的 `x`、`y`、`size`，坐标口径同头像）只收 JPEG/PNG，只限自建食物，预置食物返回 403；`DELETE /api/foods/{id}/image`；`GET /api/foods/{id}/image?kind=thumb|full` 直出二进制，没有图时返回 404。管理端对应的是 `/api/admin/foods/{id}/image`。
- `food` 表新增 `image_key`、`image_bytes` 两列（V43）。列表的轻量模式会带上 `imageKey`；`imageBytes` 只在单条接口里有。
- 新建食物时，图片要等食物有了 id 才能上传：App 先把选好的图留在本机，保存成功后再传；如果图片没传成，食物照样保存好了。「复制为自定义」时没换图，就由新建接口的 `copyImageFrom` 让服务端复制来源的图。
- 预置食物的图片目录 `preset/` 在上传目录根下，和用户 id 目录并列；备份脚本按整个上传目录同步，不需要改。
