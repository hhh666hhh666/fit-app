# 饮食记录模块：条目级 ＋ 全自建食物库、拍照记录（图片存库）

Status: accepted

> ⚠️ **后续（2026-10-12）**：本卡「食物库完全自建、无预置、无第三方数据源」的结论已被 [ADR 0009](./0009-food-preset-data.md) **收窄**——食物库现为「系统预置（只读）＋ 用户自建」双来源；其余结论（条目级记录、拍照记录、图片存 MySQL、目标手动设、弹层动线等）不变。

> ⚠️ **后续（2026-10-14）**：本卡「拍照识别（接外部 AI 从照片估算营养）：否」的结论，对**包装营养成分表 OCR** 已放开——见 [ADR 0018](./0018-food-label-photo-recognition.md)。「AI 从饭菜照片估算营养」不做 的原结论不变（费用＋准确率两理由对结构化印刷体标签不成立）。

开启第二阶段饮食记录（nutrition）。口径经 2026-10-12 四轮需求打磨拍定：**条目级记录**——每餐从食物库里选条目、营养自动算，不搞「只填汇总数字」；**食物库完全自建**，无预置、无第三方数据源（单条填写，或 JSON 文本粘贴导入/导出）；**拍照记录**（每餐一张照片存档）要做、「拍照识别」（AI 估算）不做；**图片直接存 MySQL**；每日目标手动设；首页卡六快捷直开记录弹层，全屏「饮食」页做浏览（今日／按天翻看／趋势五指标）；饮水为可编辑步进的独立计数。

## Considered Options

- **数字级记录（每餐只填汇总热量/蛋白）**：否——看着省事，实则要自己心算营养：记得累、还记不准；条目级是把脑力活交给库。
- **预置食物库（AI 拟初稿 ＋ 人工审校，复刻预设动作套路）**：否——主人明确要全自建，库完全由自己编写、自己掌控。
- **接第三方食物数据／API**：否——国内可用源多收费或限额，拿不到也没必要。
- **拍照识别（接外部 AI 从照片估算营养）**：否——有费用、准确率一般；明确只做「拍照记录」（照片存档），两词严格区分。
- **图片存服务器文件系统**：否——存 MySQL：备份（mysqldump）一并带走、单一存储真相源；代价是库体积增长。
- **独立底部 tab ／ 自成一体的记录页**：否——六快捷直开弹层最快；全屏「饮食」页只做浏览（今日／翻看／趋势），入口在首页卡的数字/四环区域。
- **按体重自动推算目标（TDEE 式）**：否——手动设，简单直给、不引入假精度；将来可加「按体重给建议值」的便利项。
- **条目级 ＋ 全自建库 ＋ 弹层记录 ＋ 全屏浏览 ＋ 拍照记录（选定）。**

## Consequences

- 新增 nutrition 模块：迁移 V10 五张表——`food`（营养字段全集＝`docs/design/食物营养字段参考.md`，4+1 主组必填：能量/蛋白/脂肪/碳水/钠，其余选填）、`meal_log`（餐次条目，营养按当时**快照**）、`meal_photo`（每餐至多一张，MEDIUMBLOB）、`diet_daily`（当日饮水累计）、`user_setting`（图片压缩等级、饮水步进、饮食目标）。
- 前端：首页饮食卡接真；新增全屏「饮食」页、食物库页、设置页；「我的」页加「食物库」「设置」入口。
- 食物库无预置 → 冷启动库是空的，最初几周记录与建库并行（一次性摩擦，接受）。
- 图片进 MySQL → 备份与导出自动覆盖图片；库体积增长，`docs/todo/` 的数据备份项紧迫度上升。
- 「手填一笔总数」（不绑食物的快速记录）**不做**——若实践后确有需要，再评估。
- 拍照识别、单位切换（不再与营养绑定）、食物库分享等，均在「明确不做／后置评估」（scope）。
