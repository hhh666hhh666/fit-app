# 营养成分表照片识别入库：云端多模态 + 后端代理 + 确认页，照片不留只记用量

Status: accepted

> ⚠️ **后续（2026-10-14）**：本卡放开 [ADR 0008](./0008-diet-logging-module.md) Considered Options 中「拍照识别：否」对**包装营养成分表 OCR** 的适用范围——0008 否掉的是「AI 从饭菜照片估算营养」（拍一碗面猜热量），**那条结论不变**；本卡把「拍营养成分表 → 草稿 → 确认入库」立为独立功能。

拍食品包装上的营养成分表，经**云端多模态大模型**（Qwen-VL，DashScope）识别为结构化草稿，用户在**确认页**校对后入食物库；**照片不留**，只按次记 token 用量。服务器 2C2G、内存硬顶 640MB、无 GPU（还与 quizzy 共机），本地推理出局；服务器在阿里云，DashScope 同云直连、无需代理。单次识别约 0.2 分钱（8b 档），自用月成本不到一块钱，新用户另有 180 天免费 token 额度。

## Considered Options

- **自建 OCR（PaddleOCR 等）部署在服务器**：否——2C2G、640MB、无 GPU，跑不动；且中文营养成分表版面千奇百怪（表格线缺失、双语混排、竖排），解析规则要以周计地调养，准确率还没保证。
- **端侧本地模型（打进 App / WebView）**：否——模型体积几百 MB 级，WebView 壳内推理工程复杂、耗电可观；识别是低频操作，不值得常驻。
- **混合（OCR 提文字 ＋ 大模型结构化）**：否——比端到端多一跳，成本与延迟都涨，收益仅是「少传一张图」。
- **前端直连大模型 API**：否——Key 放客户端等于公开，谁都能扒走滥用；走后端代理还能顺手限流、留痕（用量表就是留痕的一部分）。
- **撞名直接覆盖已有食物**：否——会静默改掉手工校订过的营养数据且不可撤销。改为识别接口预检同名，确认页给「编辑库裏已有的 / 仍然新建（改个名）」二选一。
- **精简确认表单（只留 4+1＋标签常见项）**：否（后置）——先原样复用现有 45 字段编辑表单，零额外工程、行为与手工建库完全一致；实测确认成本高再裁，见 scope「明确不做」。
- **识别照片留存**：否——相册的语义是餐照，混进包装标签照会搅浑 20GB 配额与相册浏览；复盘准确率靠本地测试集，不靠生产照片。
- **展示费用金额**：否——只展示 token 数与请求次数；明细含输入/输出/缓存命中 token、模型、耗时，不折算钱。
- **云端 VL 端到端 ＋ 后端代理 ＋ 确认页复用编辑表单 ＋ 用量流水 ＋ 无 Key 优雅降级**（选定）。

## Consequences

- **scope「明确不做」改写**：「拍照识别（AI 从照片估算营养）」收窄为「AI 从饭菜照片估算营养」；本功能作为范围约束 #21 入表，ADR 0008 已补后续注记。
- **新增迁移（V19）`food_recognition`**：按次流水——模型档、输入/输出/缓存命中 token、耗时 ms、成败、可选关联的 `food_id`；只增不删。
- **新增接口**：识别（multipart 照片进、草稿**出不落库**，带同名冲突标记）；用量汇总（外卡两值：累计 token ＋ 请求次数）与明细分页。均走后端代理，Key 不出服务端。
- **配置 `fitapp.recognition.*`**（endpoint / model / api-key，env 注入；档位默认 `qwen3-vl-8b-instruct`，不够改配置再拿测试集验证）；**无 Key 时识别接口返回友好业务错误、前端入口给降级提示**——实现与 Key 申请解耦，管道可先搭。
- **新 Controller 必须配测试类**（CI 守卫 `scripts/check-module-tests.sh`）。
- **kJ→kcal 换算复用 JSON 导入链路的既有逻辑**：prompt 只要求模型**照抄**标签（能量 kJ、NRV% 原样输出），换算与「NRV% 是比例不是绝对值、必须剔除」都在服务端做——转录是 VL 的强项，算术不是。
- **「我的」页存储占用卡下方新增识别用量小卡**：外卡只露累计 token ＋ 请求次数；点进明细分页（输入/输出/缓存命中/模型/耗时），**不显示费用**。
- **工作量 4~7 天**（后端 1.5~2.5、前端 1.5~2.5、文档与部署杂项 0.5~1），摆动项是 prompt 打磨。
- **阻塞**：无 API Key 前准确率无法实测；Key 到位后拿 10~20 张真实标签测试集调 prompt 再定档位。

> ⚠️ **后续（2026-10-14，实现落地时收窄）**：上文「可选关联的 `food_id`」取消——保存走通用的 `POST /api/foods`，识别端链不上「哪次识别存成了哪个食物」；为它改保存接口的契约不值当。`food_recognition` 保持纯流水：用途是**用量追踪**，不是溯源。
