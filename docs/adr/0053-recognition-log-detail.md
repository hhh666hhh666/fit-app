# 识别明细可点开看详情：每次识别多记一些，连模型原文一起留

Status: accepted · 2026-11-09

主人要「识别明细」里的每一条都能点进去，看到能显示的全部信息。原来每条只存模型、输入/输出/缓存命中 token、耗时和成败，失败了也看不出为什么。这次从 V40 起每次识别多记：

- 识别入口（营养成分表入库 / 记一餐 AI 识别）
- 服务商地址（不含 Key）、当时的思考开关与思考等级
- 输出 token 里的思考部分、结束原因、服务商的请求 ID
- 发给模型的图片大小与格式
- 识别出的名称（成功时）、给用户看的失败原因（失败时）
- **模型原始输出**（响应里模型回答的那段文字），截到 16000 字
- **发送的请求体**与**收到的完整响应**（V41）：请求体与实发一致，只把图片的 base64 换成「已省略：N 字节」占位，API Key 在请求头里、不在请求体中；响应失败时是 HTTP 状态加报错正文

## Considered Options

- **只在前端把现有几项排版得更细**：否——现有信息太少，点进去也看不出为什么失败。
- **把识别用的照片也留下**：否——[ADR 0018](./0018-food-label-photo-recognition.md) 定过照片不留（相册语义与空间配额），这次不改。
- **原始输出也放进列表接口**：否——一条可能十几 KB，列表分页一页 50 条，只有详情接口查它（请求体、响应全文同理）。
- **请求体里连图片 base64 一起存**：否——一张图几百 KB 到几 MB，进库就是变相留照片，与 ADR 0018 冲突；换成写明字节数的占位。
- **多记上面这些，详情页单独查一条**（选定）。

## Consequences

- 迁移 V40：`food_recognition` 加 12 列；V41 再加请求体与响应全文两列；全部可空；老记录不回填，详情页显示「未记录」并说明是更新前的记录。
- 新接口 `GET /api/food-recognition/logs/{id}`（只能看自己的）；列表接口不带 `rawOutput`。
- 新页面 `pages/recognition-log/detail`：结果、模型与参数、Token（缓存命中 / 未命中 / 思考分项）、耗时与图片、服务商回执、模型原文、发送的请求、收到的响应（JSON 自动排版，可复制；请求与响应默认收起）。
- 模型原文属于主人自己的数据，和流水一样只增不删；注销账号时随用户数据一起删除（与其他用户数据同一路径）。
