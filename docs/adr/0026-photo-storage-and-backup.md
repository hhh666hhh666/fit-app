# 餐照移出数据库 ＋ 备份策略（每日快照与异地副本）

Status: accepted

## 背景

两件事纠缠在一起，必须一起解：**图片把库撑成了备份做不下去的形状**，而**此前根本没有任何自动备份**。

**其一：图片是唯一会持续长大的数据。** 库内 `data_length + index_length` 只有 1.4 MB，而 `meal_photo` 里
两张餐照的 `image + thumb` 合计 12.77 MB——`mysqldump` 导出的 15 MB 里几乎全是它们的十六进制文本。
需求已定图片上限 **20 GB**（ADR 0013），而 `mysqldump` **不支持排除列**，于是：

- 导出文本约 2 倍膨胀 → 触顶时单次导出要先在磁盘上生成约 40 GB 的中间流；
- 服务器可用磁盘只有 **27 G**（40G 盘已用 11G）——这条「每日全量」会在某天**突然失败**，而不是优雅降级；
- 还有一层：`--single-transaction` 会开一个长事务读快照，图片越多快照越久，在**这个 2C2G 的共享实例**上
  会连带拖慢 quizzy（同一个 MySQL 容器，ADR 0005）。

**其二：出事会真的疼，而且已经在疼了。** 部署脚本 `server-deploy.sh` 每次跑到备份那一步都会打印
「⚠️ 没有 backup-mysql.sh，跳过部署前备份」——钩子早就留好了，脚本一直没人写。2026-10-16 一天之内
就手工 dump 了两次（v0.8.3、v0.9.0 发版前，两批迁移都要改数据），`deploy/README.md` 那句
「回滚只换代码、不回滚数据库，所以部署前必须先备份」全靠人记着。**一天两次手工备份说明的不是流程稳，
而是漏一次就没有回滚点。**

## 决策

1. **图片实体存服务器文件系统**，库里只留相对路径与元数据（`meal_photo.path` / `thumb_bytes`）。
   路径键 `{userId}/{logDate}/{meal}` 与唯一键 `uk_mp_user_date_meal` 同构——「重拍即替换」天然是
   同路径覆盖，不堆孤儿，也不会随重拍留下读不到的旧格式文件（写入前清掉候选扩展名）。
   扩展名跟随 `mime`，所以同一餐换成 png 时旧 jpg 会被清掉。

2. **搬迁随应用启动执行**（`MealPhotoFileMigrator`），而不是放进 SQL 迁移。
   落盘需要文件系统与挂载卷，而这些只有应用进程有；Flyway 阶段够不着。由此定了三条约束：
   **幂等**（按 `image IS NOT NULL` 挑待搬行，搬完置 NULL）、**不丢数据**（先落盘、成功才清库里的 BLOB，
   任何一步失败原图都还在库中、下次启动自动重试）、**不阻断启动**（单张失败只记日志）。

   其中最关键的一道闸：**启动时自检存储目录是不是挂载点**（读 `/proc/mounts`）。若没挂载宿主机卷，
   落盘会写进容器可写层、容器重建即丢，而那时库里的 BLOB 已被清空——图片将永久丢失。
   所以检测到「没挂载」就**中止搬运**（图片原样留在库中），挂好卷后重启会自动继续。

3. **备份分两条线，语义不同**：

   | | 库（结构化数据） | 图片（文件目录） |
   |---|---|---|
   | 体量 | KB 级 | MB → 上限 20 GB |
   | 变化 | 天天变 | 写一次基本不变（仅重拍时覆盖） |
   | 手法 | **每日全量 dump** | **每日硬链接快照** |
   | 保留 | 30 份，每份可独立恢复 | 30 份，未变文件在册子间共享 |

   图片用快照而不是 `rsync --delete` 镜像，是因为镜像只有「最新状态」：手滑删一张，同步会把删除也照做一遍，
   备份里那张跟着没了——没有后悔药。快照每天留一册（`--link-dest` 硬链接），既能翻回任何一天的样子，
   每天新增占用又只等于「当天新拍的那点量」（实测：源 6.3 MB，两册快照合计仍是 6.3 MB）。

4. **顺序定成「先图片、后数据库」**（03:30 图片、03:35 库）。两者没法在同一瞬间完成，顺序决定
   「万一卡在中间」的最坏结果：先图后库最坏是多一张没人认领的图片（无害，重拍覆盖或清理脚本收走）；
   反过来会出现「账本上写着有这张照片、翻开相册却没有」（空号，最麻烦）。

5. **异地副本走对象存储（阿里云 OSS，与服务器同地域走内网）**。它治的是「服务器整个没了」，
   与快照的职责不同，所以**只推当前状态、不留历史版本**——OSS 没有硬链接，把 30 册快照推上去
   会变成 30 份完整拷贝（占用放大 30 倍）。历史版本由本地快照负责。选 OSS 而非「拉回本机」的理由是
   **不依赖任何一台机器常开**：本机不是常开，那个方案迟早退化成「靠人记得」，而这件事刚被证明不可靠。

6. **恢复演练挂进发版流水线**（`restore-verify.sh`，部署后跑）。判据刻意**不是**「行数与线上库相等」
   （备份比当前早，本就该不同），而是：导入全程无错、恢复出的表数量与线上一致、预置数据表非空
   （dump 若被截断成空壳，这一条会兜住）。理由：「dump 命令返回 0」只说明它没崩，不说明导出的东西能用。

## Considered Options

- **继续把图片放库里（BLOB），只加「体积闸」**：否——闸只能把「突然失败」变成「届时可控切换」，
  并不能让备份真的跑得动；而且迁移那天照样要落盘或进对象存储，等于把同一件工作推到更急的时候做。
- **图片落服务器本地磁盘**（选定）：成本最低的一次拆分，库回到 KB 级、图片天生适用于增量同步。
- **服务器上自建 MinIO**：否——看着像「既对象存储又不怕厂商绑定」，但对这个项目是**伪解**：
  磁盘还是那 40G，20 GB 上限照样吃掉大半。它解决的是 API 形态，不解决容量与故障域。
- **立刻把图片放进对象存储（线上就直接存 OSS）**：否，作为**终局**保留——现在只有 2 张图，
  为它开桶、配密钥、改链路（含私有图的签名 URL）投入与保护的数据不成比例。触发条件写进 Consequences。
- **异地用「本机手工拉」**：否——零成本，但依赖「你记得做」。
- **异地只用服务器本地**：否——不防整机故障与磁盘损坏，而那是两种最常见的真实事故。
- **(曾被否) 复用 `reps` 栏存爬楼层数**：与本题无关，但同属「别让一个字段担两套语义」——见 ADR 0025。

## Consequences

- **实测：图片出库让 dump 从 15 MB 降到 119 K**（同一天、同一个库，V25 前后各备份一次）。
  这正是整个改造的目的——「每日全量」从「迟早跑不动」变成秒级的事。
- **恢复演练会在生产 MySQL 实例上占内存**，而它与 quizzy 共用、容器内存上限只有 384 MB。
  v0.10.0 首次上线实测：一份含 12.77 MB 餐照的 **15 MB** dump 灌入时把 mysqld 撑爆，
  内核 OOM-killer 直接杀了它（`dmesg` 里 `oom_memcg` 指向 quizzy-mysql 的 cgroup），容器随之重启——
  **发布被标红，而部署其实完全成功**（容器已切版本、迁移跑到 V25、图片也搬完了）。
  两处修正：脚本加**体积闸**（默认 8 MB，超过就跳过并说明；图片出库后 dump 只有 119 K，本就触发不到），
  流水线里这一步改成 `continue-on-error`——它是**体检**，不是发布的成败判据。
- **备份范围含同实例的另外两个库**（2026-10-17 补）：`fit_app` 与 `quizzy`、`mysql` 系统库
  **共用同一个 MySQL 实例**，故障域完全相同，所以每日任务也覆盖它们——quizzy 用它**自己的**脚本
  （那是它仓库管的东西，这里只调用、不改它），系统库用新增的 `backup-system-mysql.sh`。
  补这一条是因为核出一个没道理的不对称：此前只有 fit_app 有每日备份，quizzy 停在「发版时顺带备一次」
  （最新一份停在 3 天前），而 `mysql` 系统库（账号与权限）三个项目都没人备。
  ⚠️ 触发方式用的是 **crontab**，而 quizzy 原定的是 **systemd timer**（它 2026-10-01 的决策，理由是好查
  status/logs）——落地时只核了它的脚本能否被调用、没查它的决策卡。偏差不影响备份文件本身，
  接 OSS 重做调度时一并换回；完整记录在它那边的 `docs/operations/backup.md` 与待办里，这边只留指向、不维护第二份。
- **⚠️ 多出一个失败面：卷必须持久化。** 之前「账本在哪、照片就在哪」，照片跟着库一起受保护；
  现在照片放在 `/srv/fit-app/uploads`，compose 里必须**绑定挂载**（`/srv/fit-app/uploads:/data/uploads`，
  不是匿名卷）。挂错的后果是「库还在、照片全没」。搬迁器的挂载自检只是**搬迁那一次**的护栏，
  日常上传不经过它——所以这一条靠部署配置与验证清单保证。
- **库与文件不再事务一致**：删除时**先删行、后删文件**（反过来会留下「记录指向不存在的图」，
  比留个孤儿文件麻烦得多）；漏删只产生无害的孤儿文件。
- **`image` / `thumb` 两列保留但恒为 NULL**，不删。原因：删列不可逆，而落盘必须在应用运行时做；
  列留着但为 NULL 不占空间，库体积的收益已经拿到。确认线上无残留后再单独一个迁移清理（见待办）。
- **备份单元从 1 个变成 2 个**，且**必须同时上线**：图片出库后，只上图片快照或只上库备份
  都会得到「有账本没相册」或反之。过渡期（图片还在库里）则相反——库 dump 天然含图片，一条线就够。
- **服务器上 `.env` 多一个 `OSS_BUCKET`**；ossutil 的凭据只存在于服务器，不进仓库。
- **图片将来若迁 OSS**：触发条件定为「`meal_photo` 总量达 500 MB 或 1000 张」。届时只需换掉
  「图片线」的实现（快照 → 不必再备），结构化线一行不动——这正是把备份按两线设计的用意。
