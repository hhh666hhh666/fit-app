# 外部 agent 只读取数接口：不做增量、不限时间范围

Status: accepted · 2026-10-30

需求：主人自己运行的 agent 要拉取尽可能全面的数据，用来分析身体情况，可以取全部或指定时间。现状只有 7 天过期、不可吊销、可读可写的 JWT，也没有面向机器的取数接口。本卡为外部 agent 开一个只读口子，App 的取数与缓存（[ADR 0035](./0035-client-cache-and-invalidation.md)）不变。

## Considered Options

- **沿用 JWT**：否——要保存主人密码，7 天过期，不可吊销，还能写数据。
- **OAuth 授权**：否——调用方就是主人自己的 agent，没有第三方授权场景（[ADR 0001](./0001-self-use-tool.md)）。
- **令牌写在 `.env`**：否——吊销要登服务器改配置并重启，手机上做不到；健康数据值得多一张表。
- **增量：更新时间 ＋ 墓碑表**：否——主人拍板不做。要补列、修更新时间、在删除路径写墓碑，约多三成工作量；agent 靠重拉覆盖就能拿到改和删。
- **增量：统一变更流水**：否——全部写路径都要埋点，漏一处就静默丢数据。
- **一个接口返回全部**：否——当前状态没有时间概念，和时间范围参数混在一起语义不清。
- **按域拆多个接口**：否——agent 要调很多次，一次分析的数据也不再一致。
- **历史按 90 天分块、靠 `nextFrom` 循环拉取**：否——主人定先不设时间上限；内存改由服务端流式输出兜住。
- **输出表结构原样**：否——爬楼组的占位值 0 和 1 会被当成真实成绩。
- **给计划、个人档案、饮食目标加历史表**：否——要动全部写路径；要长期对比时由 agent 保存每次的快照。
- **内嵌 base64 餐照**：否——体积大，而且不是每次分析都要看图。
- **做 MCP**：否——REST 已够用，MCP 可以以后在外面包一层。
- **接口文档写死在前端**：否——agent 也要读同一份，两处必然漂开。
- **当前状态与历史两个 REST 接口，只读专用令牌，服务端流式输出，文档由后端统一提供**（选定）。

## Consequences

**接口**

- `GET /api/agent/current`：个人档案、计划、周安排、饮食目标、口径说明。这些数据没有时间线，不受时间过滤，一律是当前值。
- `GET /api/agent/history?from=&to=`：一次训练、餐次条目、身体档案、饮水、餐照元数据、每日汇总，并附上被引用的动作和食物，以及主人自建的动作和食物。
- `GET /api/agent/photos/{date}/{meal}` 与 `.../thumb`：取餐照原图与缩略图。
- `GET /api/agent/docs`：接口文档（Markdown），公开访问，不含任何用户数据。
- 排除：预置食物全集、食物组合、标签识别用量、账号信息、其余设置项。

**时间与覆盖**

- `from`、`to` 为 `YYYY-MM-DD`，两端都包含，都不传就是全部历史；时区固定 Asia/Shanghai。
- 一律按业务发生时间归属：训练按开始时刻（跨零点算开始那天），饮食、饮水、餐照按记录日期，身体档案按测定时刻。
- 响应是这个时间范围的**完整结果**，agent 应整段覆盖本地数据，被删除的记录靠重拉消失。子行 id 不稳定，不对外承诺。

**字段与派生值**

- 字段语义化：爬楼组的重量和次数返回 null、只给层数；直接带肌群和记录口径；标明单位和时区；带 `schemaVersion`。
- 给原始事实、已落库的值（总容量、PR 标记、手填训练消耗）和简单求和。
- 每日汇总只收至少有一条饮食、饮水或训练记录的日子：摄入四项合计、饮水量、训练消耗、每日总消耗拆解（按 [ADR 0042](./0042-daily-energy-weight-as-of-date.md)，含所用体重及其日期；不能计算时给出缺什么）、热量缺口、当天条目数和已记录的餐次。
- 口径说明写明「记录可能不全，缺口只是粗略参考」。饮食目标不进每日汇总：它没有历史，放进去会被误读成当时的目标。
- 食物的完整营养与 GI 是**当前值**，须标注；饮食记录只快照了热量和三大营养素，食物已删除的条目只有这四项。

**鉴权**

- 每个用户一把令牌，只存哈希，明文只在生成时显示一次；重新生成时旧的立即失效。
- 令牌只能访问 `current`、`history` 和餐照；生成、吊销、查看状态走登录态 JWT。
- 只记最后使用时间，不做限流和访问日志。
- 令牌校验失败返回真实的 **401**，响应体仍用统一信封；App 的现有接口继续走 HTTP 200 加业务码。

**内存与失败**

- 生产后端堆上限只有 256 MB，`history` 必须分批读库、流式写出，不能先组装完整结果。
- 流式写出后无法再改状态码，中途失败时响应会被截断，agent 要把 JSON 解析失败当作本次拉取失败并重试。
- 整次拉取不在同一快照内，期间发生写入可能造成轻微不一致；单用户下接受。
- 本机实测（2026-10-30，与生产相同的 JVM 内存参数，5 年合成数据：1000 次训练、18250 条饮食）：全量约 8.6 MB、1～1.7 秒，4 个并发也没有撑大堆，进程常驻内存约 250 MB（生产上限 640 MB）。共用 MySQL 在生产上的表现未验证，见[待办](../todo/2026-10-30-TODO-外部agent数据接口.md)。

**手机端**

- 「我的」页加一张外部 agent 小卡，只显示令牌状态；点进独立页面管理令牌（生成、吊销、最后使用时间）和看接口文档。文档内容来自 `GET /api/agent/docs`，可一键复制给 agent。把操作放进详情页，是因为明文令牌要占一块显示区，不该挤在 tab 页上。
- 这份文档是 [API 文档](../design/API.md)「不维护 endpoint 表」的例外：外部调用方拿不到本仓库，需要一份随后端发布的说明。文档与实现同改。
