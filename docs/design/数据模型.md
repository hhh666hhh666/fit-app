# 数据模型

**目的**：讲清实体之间怎么连、生命周期怎么走，以及哪些约束是「写查询时必须知道的」。

**读者**：改数据结构或写查询的人。

**真相源**：**表结构以迁移脚本为准**（`backend/src/main/resources/db/migration/`）。本文**不复制建表语句**，只写意图与约束。

## 实体关系

<!-- 一张简表：实体 → 它属于谁 → 与谁关联 → 谁删了它跟着走。 -->

| 实体 | 归属 | 关联 | 删除时的连带 |
|------|------|------|--------------|
| user | —（自用起步；表已带用户维度） | — | 暂无删除功能 |
| exercise | 预设（`user_id` 为空）／用户自定义 | 被 `workout_block.exercise_id`、`plan_exercise.exercise_id` **弱引用**；`metric`＝**记录口径**（默认 `weight_reps`＝重量×次数；爬楼为 `floors`＝层数，V24 加，[ADR 0025](../adr/0025-cardio-metric-and-floors.md)） | **不物删**：删除＝`archived=1` 下架，历史继续显示（scope #10） |
| plan | user | 含 `plan_exercise`；`name` 同用户内不重名（服务端校验） | **物理删除**：连同编排；周表引用一并清空（scope #10 细化口径） |
| plan_exercise | plan | 引用 exercise（弱）＋ `name`/`muscle` **快照兜底**；`sort_order` 编排顺序；三层目标 `target_sets`/`target_reps`/`target_weight`（均可 NULL） | 随 plan 删 |
| week_schedule | user | `day_of_week` 0=周一…6=周日，每用户每天至多一行（唯一键）；`plan_id` 弱引用 | 引用的 plan 删除时删行 |
| body_record | user | 一次测定（体重与四围记哪项填哪项，至少一项）；体重内部统一为 kg，展示单位由设备偏好转换；`measured_at` **精确到分**（V18，`DATE`→`DATETIME`），允许同日多条（时刻＋note 区分场景） | **物理删除**（支持批量删）；可整条编辑 |
| workout | user | 含 `workout_block`；`title` 为当次标题快照；`plan_id` 为**来源计划弱引用**（自由训练为 NULL）；`total_volume`＝Σ(重量×次数) 且**只累计力量动作**（有氧不计入，历史值由 V23 重算，[ADR 0023](../adr/0023-volume-metric-scope-and-display.md)）；该记录可在详情页**整体编辑**（标题/备注/组次覆盖，重算总容量与 PR） | 物理删除（连同 blocks／sets；支持批量删） |
| workout_block | workout | 含 `workout_set`；引用 exercise（弱）＋ `exercise_name` 快照兜底 | 随 workout 删 |
| workout_set | workout_block | —（`set_index` 从 1 起、每个 block 内重置）；`pr`＝提交时刷新该动作历史最佳（**重量优先、同重量比次数**，[ADR 0024](../adr/0024-pr-definition-heaviest-set.md)；**有氧动作与未挂库的组不判定**；编辑该记录时按同口径重判，历史基线**排除本记录自身**；历史值由 V23 按时间序回放重打）；`duration_sec`＝该组净用时（秒，剔除暂停段；**可空**＝无用时）；`floors`＝层数（`metric=floors` 的动作专用，V24 加；这类组的 `weight`／`reps` 存占位值 0／1，消费方一律以 `floors` 为准，[ADR 0025](../adr/0025-cardio-metric-and-floors.md)） | 随 block 删 |
| food | 预置（`user_id` 为空）／user | `user_id` 空＝**系统预置**（只读，与 exercise 同范式）；非空＝所属用户；`category` 仅预置使用；`view_count`＝浏览次数（详情页每查看一次 +1）、`favorite`＝收藏（置顶标记）——**两者对预置都是全局共享**（预置行全系统一份）；食物库列表排序＝**收藏 → 浏览次数降序 → 名称**；`name` 仅同用户内唯一（预置允许同名）；营养全集 45 项（用户自建 4+1 必填；预置的 `sodium` 可为 NULL＝未测，见[《食物营养字段参考》](./食物营养字段参考.md)）＋扩展字段 **GI**（选填、非负、1 位小数、**不限上限**） | 用户自建**物理删除**——历史靠 meal_log 快照自足；预置不可改删（服务端拦截，可「复制为自定义」） |
| food_combo | user | 组合名；`name` 同用户内不重名（服务端校验）；含 `food_combo_item`；编辑时明细**整体覆盖** | **物理删除**（连同明细）；不影响历史（历史是 `meal_log` 快照） |
| food_combo_item | food_combo | 引用 food（**弱引用**）＋ `food_name` 快照 ＋ **固定克数** `grams`；`sort_order` 为组内顺序（加入一餐时按此顺序落库）；**不存营养快照**——整份热量按 food 现值现算，食物被删的条目不参与折算（仍列出名字） | 随 food_combo 删 |
| meal_log | user | 引用 food（弱）＋ `food_name` 与 **per100 四值快照**＋实际克数；`log_date`＋`meal`（早/午/晚/加餐） | 无连带 |
| meal_photo | user | `log_date`＋`meal` 唯一（每餐一张，重拍即替换）；`image`＝原图 MEDIUMBLOB（前端已压缩）、`thumb`＝上传时**后端生成**的长边 ≤320 缩略图（老数据为 NULL，读取回退原图）；照片总占用有上限（`fitapp.storage.photo-quota-bytes`，默认 20 GB），达上限**拒绝上传**（[ADR 0013](../adr/0013-photo-storage-and-quota.md)） | 无（可单张删除） |
| diet_daily | user | `log_date` 唯一（每日饮水累计） | 无 |
| user_setting | user（唯一一行） | 图片压缩等级／饮水步进／饮食目标五值；行不存在时读默认 | 无 |
| food_recognition | user | 标签识别用量流水（[ADR 0018](../adr/0018-food-label-photo-recognition.md)；迁移 V19）：每次调用一条——模型档、输入/输出/缓存命中 token、耗时 ms、成败；**只增不改不删**；不关联 food（保存走通用接口，链不上——见 ADR 0018 后续注记） | 无连带 |

## 关键语义与坑

- **周安排一格三态**：`plan_id` 有值＝练该计划；`is_rest=1`＝休息（此时 `plan_id` 必为 NULL）；**无行＝未安排**。三态都由服务端 `PUT /api/schedule/{day}` 归一，前端 `DaySlot = 计划id | 'rest' | null` 一一对应。
- ⚠️ **`week_schedule` 把某天从「计划」改成「休息」时必须强写 `plan_id=NULL`**：全局 `not_null` 更新策略会静默跳过 null 字段，必须用 `LambdaUpdateWrapper.set(...)`（`ScheduleService` 有注释；`ScheduleServiceTest` 有守卫用例）。换 `updateById` 会留脏 `plan_id`。
- **删除机制为何不同**（scope #10 细化）：动作被 `workout_block` join 显示（动作行必须存在）→ 只能下架；计划的展示完全靠快照（`workout.title`、`plan_exercise.name/muscle`）→ 物理删除不影响历史，且避免「已下架计划还能不能开练」的新问题。
- **PR 两层口径**（scope #7）：`workout_set.pr` 是「提交（或编辑保存）时点」的历史布尔（之后不回改，历史日志里「当时是 PR」恒真；编辑某条时按「排除该条自身」的历史基线重判）；「各动作当前最佳」由统计接口按 `MAX(weight×reps)` 现算（并列取最近），不依赖 pr 列——两者永不矛盾。
- **计划列表卡「上次」**：`PlanMapper.selectListItems` 用两条同条件子查询取「最近一条 `workout`（`plan_id` 匹配）」的时间与总容量——计划改名不影响（按 id 匹配）。
- **GI 是 food 上的扩展字段**（`V11`）：不在国标营养标签的 45 项里（[《食物营养字段参考》](./食物营养字段参考.md) 单开了「本表之外的扩展字段」节），只能挂在一个食物上——**不进 `meal_log` 快照、不参与四环与趋势**。要用「每日升糖负荷」（≈GI×碳水÷100）这类指标时按现有数据现算，不落列。
- **食物库两种来源**（[ADR 0009](../adr/0009-food-preset-data.md)）：`user_id` 空＝**系统预置**（《中国食物成分表》＋ GI 表，约 1800+ 条；只读，可「复制为自定义」），非空＝用户自建。列表/搜索两种合并返回（另有 lite 轻量模式＋limit，预置量大不宜全量拉）；导出只导自有、导入查重只看自有；预置可直接被 `meal_log` 引用（快照照写、四环不受影响）。预置里名字带 `*` 的＝营养数据由公开资料补全，可信度低一档。
- **饮食两层快照**（[ADR 0008](../adr/0008-diet-logging-module.md)）：`meal_log` 存 **per100 四值快照 + 实际克数**——`food` 改删都不影响历史与趋势（实际值 = per100 × grams ÷ 100，服务端现算）；`food_id` 仅弱引用。
- **食物组合是「批量添加的快捷键」**（[ADR 0012](../adr/0012-food-combo.md)）：`food_combo_item` 只记「哪样食物、多少克」，**不存营养快照**——组合卡片的整份热量、以及加入一餐时写下的快照，都由服务端按 `food` **现值**算。所以改食物会影响组合的展示，但不影响已记录的历史。「整份加入」＝一次事务插入多条**普通** `meal_log`（`POST /api/diet/meals/batch`），**不新开记录类型**。
- **照片存库**：`meal_photo.image` 是 MEDIUMBLOB（前端压缩后上传；读取接口直出二进制、不走 Result 信封）；`mysqldump` 备份会一并覆盖图片——见 `docs/todo/` 数据库备份项。
- **设置行懒创建**：`user_setting` 行不存在时读取返回默认（medium / 250ml / 目标全空），首次保存才落行；**目标可清空**——走显式 `set`（not_null 坑，同 `week_schedule`）。
- **识别用量是流水不是账本**（[ADR 0018](../adr/0018-food-label-photo-recognition.md)）：`food_recognition` 按次记 token（输入/输出/缓存命中**单列**——DashScope 隐式缓存命中部分单价不同，混记算不清）、模型、耗时；「我的」页小卡只露累计 token 与请求次数，明细分页看逐条；**不折算费用**（拍定口径）。失败的调用也记——token 真实花了。
- **三层目标是「预填默认值」不是约束**（[ADR 0007](../adr/0007-session-set-flow-and-target-weight.md)）：会话页按 `target_sets` 铺行、`target_weight`/`target_reps` 预填；训练中怎么改都不回写计划（scope #9）。
- **训练会话不在库里**（[ADR 0020](../adr/0020-session-local-persistence-and-wall-clock-timer.md)）：进行中的那一段只存在客户端本机（`frontend/src/utils/session.ts`），「结束训练」时一次性提交落库。后端**没有**「草稿会话」表、也没有增量保存接口——这是有意的，不加表、不加发布链路的负担。
- **组次用时与训练时长同口径**（[ADR 0022](../adr/0022-session-pause-and-set-duration.md)）：两者都是**净时间**（剔除暂停段），所以「各组用时之和」与 `workout.duration_sec` 可比。`workout_set.duration_sec` 可空——全部历史数据都是 NULL，编辑（整体覆盖）时没填用时的行也存 NULL，前端据此不显示用时。
- **身体档案「列表看最新、图表看当天最小」**（[ADR 0017](../adr/0017-body-record-model-and-crud.md)）：体重卡大字＝**最新一条**的实测值，**不参与**按日聚合；两个图表序列都是日粒度、同一天取最小值。两处同名不同义——`weightSeries`/`girthSeries` 的点 `date` 是 `LocalDate`，明细行的 `date` 是 `LocalDateTime`。
- ⚠️ **前端给后端的时间串必须 ISO 带 `T`**（`2026-10-13T23:51:00`）：`spring.jackson.date-format` 管不到 `LocalDateTime`，空格分隔会 400（实测确认，口径见 `application.yml` 里那条注释）。

## 通用约定

- 所有表默认 `utf8mb4`，主键 `BIGINT AUTO_INCREMENT`，时间字段用 `DATETIME`。
- **逻辑删除还是物理删除**：本项目默认**物理删除**；例外（动作下架）见上表与 scope #10。
- **历史一致性**：引用会被修改的内容时（快照类字段），「改了源之后历史显示什么」必须明确并写进 ADR。
- **Java 侧置 NULL**：MyBatis-Plus 全局 `update-strategy=not_null`——实体 `updateById` 会**静默跳过 null 字段**；要写 NULL 一律用 `LambdaUpdateWrapper.set(column, null)`。

## 加迁移脚本的规矩

- 文件名 `V<N>__<snake_case>.sql`，`N` **严格递增**，已上线的脚本**永不修改**（要改就加一条新的）。
- 加 `V5` 及以上编号的脚本后**必须重启后端**才能生效（Flyway 在启动时迁移）。
- 迁移脚本里的破坏性操作没有保险，**靠人守**。
- **含中文数据的迁移，注意验证通道的字符集**：实际执行走 Flyway + JDBC（字符集由连接 URL 指定，正确）；但发布流水线的迁移重放走 **mysql CLI**，其默认连接字符集可能是 latin1——一个汉字被算成 3 个字符，VARCHAR 长度凭空 ×3。若 CLI 下报 `1406 Data too long` 而本机 Flyway 正常，先查 `--default-character-set`（`release.yml` 迁移重放段有注释与先例：v0.4.0 的 V13 即此坑）。
